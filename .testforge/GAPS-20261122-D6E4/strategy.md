# Test strategy: GAPS-20261122-D6E4 Keep API tests in step with the spec

Revision 1 · generated by TestForge

## Summary

The Orders API spec documents GET /products/{id} (getProduct) and POST /orders/{id}/cancel (cancelOrder), but no test calls them. Add Vitest API tests (real app in-process, as the existing specs do) for each one's success response and every error response the spec documents (404 for both, 409 for cancelling an already-cancelled order). Running the suite also showed that the existing GET /orders/{id} test still asserts the old `totalCents` field, while the spec (and the app) now return `total: { amount, currency }`. That test gets updated to the current contract.

## Scope

**In scope**
- GET /products/{id}: 200 Product and 404 Error
- POST /orders/{id}/cancel: 200 Order (status cancelled), 404 Error and 409 Error
- Updating the existing GET /orders/{id} success test from totalCents to the spec's total Money object, keeping all its other checks

**Out of scope**
- Operations that tests already call (listProducts, placeOrder), apart from the stale getOrder assertion
- Changes to the spec or the application
- Restructuring the existing specs (e.g. a shared server helper); listed as a follow-up only

## Environment

No external services. Each spec starts the app in-process on an OS-chosen port and fetches against it.

## Assumptions

- The app runs for real, in-process: createApp() listens on port 0 in each spec file, as test/products.test.js and test/orders.test.js already do. Nothing is faked.
- Each createApp() gets a fresh in-memory store, so each test creates the order it cancels and asserts only on that order.
- The new tests go into the existing spec files beside each resource's tests (getProduct in test/products.test.js, cancelOrder in test/orders.test.js). They reuse those files' server setup instead of copying it.
