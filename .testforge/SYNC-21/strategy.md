## Test case detail

### TC1: retries a failed call after a back-off

*unit · vitest · regression · high priority* — covers AC1

**Steps**
1. Mock task rejecting once then resolving 'ok'
2. Call retry(task) with defaults
3. Wait with vi.waitFor until the task has been called 2 times
4. Assert result resolves to 'ok'

**Expected:** task called twice; result resolves 'ok'; passes 20/20

**Rationale:** Cause: the test sleeps a fixed 40ms, but retry's back-off is retryDelay(0) = 20ms + Math.floor(Math.random()*40) jitter, i.e. 20–59ms, so whenever the jitter exceeds ~20ms the second call hasn't happened yet ('expected 2 times, got 1'). Fix: wait for the condition (vi.waitFor on the call count) instead of a fixed delay.

### TC2: stops telling a handler once it unsubscribes

*unit · vitest · regression · high priority* — covers AC2

**Steps**
1. Subscribe a handler to 'records' and call the returned stop
2. Publish on 'records'
3. Assert 0 handlers reached and handler not called

**Expected:** publish returns 0, handler not called, in any shuffled order; passes 20/20 with shuffle

**Rationale:** Cause: order dependence via shared module state. src/subscribers.js keeps one process-wide handlers Map; 'tells every handler subscribed to the topic' subscribes two handlers to 'records' and never unsubscribes, so when CI's shuffle runs it first, this test's publish reaches 2 ('expected 2 to be +0', only under certain seeds). Fix: every test removes the subscriptions it makes (onTestFinished with the returned stop), so no test leaks handlers to another.

### TC3: resolves with the ids in the order of the records

*unit · vitest · regression · high priority* — covers AC3

**Steps**
1. saveAll two records through createRecordsClient
2. Fetch each returned id
3. Assert names are ['first','second']

**Expected:** Currently fails ~40% ('expected [second, first]'); quarantined with it.skip and a comment until src/bulk.js is fixed

**Rationale:** Cause is in application code: saveAll in src/bulk.js runs saves concurrently and does ids.push(await client.save(record)), so ids land in completion order; the records client's latency is random, so the second save often finishes first. The doc comment promises record order. A test change can't fix it without hiding the bug: quarantine (skip) with a comment, record the defect and file an issue.
