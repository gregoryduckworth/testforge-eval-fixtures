# Test strategy: SYNC-21 Flaky tests on main

Revision 1 · generated by TestForge

## Summary

Three tests flake on main (CI runs `vitest run --sequence.shuffle`). The retry test uses a fixed 40ms sleep but the back-off is 20–59ms. The subscribers test shares the module-level handler map with another test that never unsubscribes, so it fails when shuffled after it. saveAll in src/bulk.js pushes each id when its save finishes rather than at the record's index, which is an application defect. Fix the two test bugs at their cause; quarantine the third, record the defect and file an issue.

## Test case detail

### TC1: retries a failed call after a back-off

*unit · vitest · regression · high priority* — covers AC1

**Steps**
1. Task rejects once, then resolves 'ok'
2. Call retry(task)
3. Wait until the task has been called twice (vi.waitFor), not a fixed 40ms
4. Assert the result resolves to 'ok'

**Expected:** task called twice; result resolves 'ok'

**Rationale:** Cause: a fixed 40ms setTimeout sleep, but retryDelay(0) is 20ms plus up to 39ms of random jitter (20–59ms), so the second call often hasn't happened yet (probe: 4/10 failures, 'called 1 times'). Fix: wait for the condition (second call) with vi.waitFor.

### TC2: stops telling a handler once it unsubscribes

*unit · vitest · regression · high priority* — covers AC2

**Steps**
1. Subscribe a handler to 'records' and unsubscribe it
2. Publish on 'records'
3. Assert 0 handlers reached and handler not called

**Expected:** publish returns 0; handler never called

**Rationale:** Cause: order dependence on shared module state. src/subscribers.js keeps one process-wide handler map, and 'tells every handler subscribed to the topic' subscribes two handlers to 'records' without unsubscribing; under CI's --sequence.shuffle it sometimes runs first, so publish returns 2 (probe: 5/10 failures, 'expected 2 to be +0'). Fix: every test registers its unsubscribe functions and an afterEach calls them, so no test leaves handlers behind.

### TC3: resolves with the ids in the order of the records

*unit · vitest · regression · high priority* — covers AC3

**Steps**
1. saveAll two records via createRecordsClient
2. Read each id back
3. Assert names are ['first','second']

**Expected:** Names in record order; currently fails sometimes because of the app defect, so quarantined with it.skip

**Rationale:** Cause in application code: saveAll (src/bulk.js:9) does ids.push(await client.save(record)) inside Promise.all, so ids are in completion order, and the client's random latency reorders them (probe: 2/10 failures, ['second','first']). The test is right; quarantine it with it.skip and a comment, record the defect, file an issue.
