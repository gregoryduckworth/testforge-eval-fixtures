# Test strategy: SYNC-21 Flaky tests on main

Revision 1 · generated by TestForge

## Summary

Three tests named in SYNC-21 pass and fail on the same commit. A probe (10 shuffled runs) confirmed each is flaky. retry: the test waits a fixed 40ms, but the back-off is 20–59ms because of random jitter. subscribers: the handler registry is shared by the whole process, and another test in the same file leaves its handlers subscribed, so the outcome depends on the shuffled order CI uses. saveAll: src/bulk.js pushes ids in the order the saves finish, not the order of the records. That is an application defect, so that test is quarantined and filed as an issue. Every existing assertion and test case is kept.

## Test case detail

### TC1: retries a failed call after a back-off

*unit · vitest · regression · high priority* — covers AC1

**Steps**
1. Use vi fake timers (restored in afterEach)
2. Call retry with a task that fails once then succeeds, with random fixed to 0
3. Check the task was called once before the back-off has passed
4. Advance the fake clock by retryDelay(0) and check the task was called twice
5. Check retry resolves with 'ok'

**Expected:** The task is called twice after the back-off, and retry resolves with 'ok'

**Rationale:** Cause: the test sleeps a fixed 40ms with a real setTimeout, but retry waits retryDelay(0) = 20ms + floor(Math.random()*40), which is 20–59ms. When the jitter goes past about 20ms, the second call hasn't happened yet (probe: 6 of 10 runs failed with 'called 1 times'). Fixing the jitter and driving a fake clock removes the timing guess.

### TC2: stops telling a handler once it unsubscribes

*unit · vitest · regression · high priority* — covers AC2

**Steps**
1. Have every test in the file register the unsubscribe function each subscribe returns, and call them all in afterEach
2. Subscribe a handler to 'records', unsubscribe it, then publish

**Expected:** publish returns 0 and the handler is not called, in any test order

**Rationale:** Cause: src/subscribers.js keeps one module-level handlers Map for the whole process. 'tells every handler subscribed to the topic' subscribes two handlers to 'records' and never unsubscribes them, so when it runs first under CI's --sequence.shuffle, publish returns 2 (probe: 'expected 2 to be +0' with 5 shuffle seeds). Unsubscribing everything after each test gives each test a clean registry.

### TC3: resolves with the ids in the order of the records

*unit · vitest · regression · high priority* — covers AC3

**Steps**
1. Keep the test and its assertions unchanged
2. Quarantine it with it.skip and a comment naming the cause in src/bulk.js
3. Record the defect and file a GitHub issue

**Expected:** The test is skipped until saveAll keeps the order of the records

**Rationale:** Cause in application code: saveAll (src/bulk.js:7-10) runs the saves concurrently and pushes each id when its save resolves. The records client has random latency, so ids come back in completion order, not record order (probe: ['second','first'] in 4 of 10 runs). The test is correct. Only the app can fix this, for example by returning the Promise.all result.
