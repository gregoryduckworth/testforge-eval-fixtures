# Test strategy: SYNC-21 Flaky tests on main

Revision 1 · generated by TestForge

## Summary

Three tests named in SYNC-21 are flaky (a 10-run shuffled probe confirmed all three). retry's back-off test sleeps a fixed 40ms while the code waits 20–59ms of random back-off. The subscribers test fails depending on order, because another test leaves handlers in the registry that the whole process shares. saveAll's order test exposes an application defect: saveAll pushes ids in the order the saves finish, not the order of the records. Fix the first two in the test code. Quarantine the third with a comment, record the defect and file an issue.

## Test case detail

### TC1: retries a failed call after a back-off

*unit · vitest · regression · high priority* — covers AC1

**Preconditions**
- vi.useFakeTimers() in this test, real timers restored in afterEach

**Steps**
1. Task rejects once, then resolves 'ok'
2. Call retry(task, { random: () => 0 }) so the delay is exactly retryDelay(0) = 20ms
3. Advance the fake clock by that delay with vi.advanceTimersByTimeAsync
4. Assert the task was called 2 times and the result resolves 'ok'

**Expected:** The task is called twice and the result resolves to 'ok' in every run.

**Rationale:** Cause: the test sleeps a fixed 40ms on the real clock, but retry waits retryDelay(0) = 20ms plus up to 39ms of Math.random jitter (src/retry.js). When the jitter pushes the delay past 40ms, the second call hasn't happened yet ('called 1 times', 7 of 10 probe runs). Fix: fake timers and a fixed random, then advance by exactly the computed back-off. The assertions stay the same.

### TC2: stops telling a handler once it unsubscribes

*unit · vitest · regression · high priority* — covers AC2

**Steps**
1. Subscribe a handler to 'records', then call the returned stop()
2. Publish on 'records'

**Expected:** publish returns 0 and the handler is not called, in any shuffled order.

**Rationale:** Cause: order dependence. src/subscribers.js keeps one handler Map for the whole process. 'tells every handler subscribed to the topic' subscribes two handlers to 'records' and never unsubscribes them. When it runs first, publish returns 2 ('expected 2 to be +0', 5 of 10 shuffled probe runs). Fix: every test that subscribes registers its stop() function for an afterEach, so no test leaves handlers behind.

### TC3: resolves with the ids in the order of the records

*unit · vitest · regression · high priority* — covers AC3

**Steps**
1. saveAll two records through createRecordsClient()
2. Fetch each id and map to names

**Expected:** ['first', 'second']. The app currently fails this, so the test is quarantined with it.skip and a comment naming the cause.

**Rationale:** Cause in application code: saveAll (src/bulk.js) does ids.push(await client.save(record)) inside Promise.all, so ids are in the order the saves finish. The client's latency is random, so the order is too ('[second, first]', 4 of 10 probe runs). The doc promises the order of the records. A test change can't fix this, so the test is quarantined, the defect recorded and an issue filed.
