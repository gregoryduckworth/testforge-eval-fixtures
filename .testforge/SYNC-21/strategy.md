# Test strategy: SYNC-21 Flaky tests on main

Revision 1 · generated by TestForge

## Summary

Three tests named in SYNC-21 pass and fail on the same code. A probe with shuffle (10 runs) confirmed all three are flaky: retry 2/10, subscribers 4/10, saveAll 5/10. Two causes are in the tests and get fixed there, with every assertion kept: a fixed 40ms sleep racing a 20–59ms back-off, and subscriptions leaked through the module-level handler list. The third cause is in application code: saveAll pushes ids in the order the saves complete, not in record order. That test is quarantined, and the defect is recorded and filed as an issue.

## Test case detail

### TC1: retries a failed call after a back-off

*unit · vitest · regression · high priority* — covers AC1

**Steps**
1. Mock a task that rejects once and then resolves 'ok'
2. Call retry(task)
3. Wait with vi.waitFor until the task has been called twice, instead of a fixed 40ms sleep
4. Assert the result resolves to 'ok'

**Expected:** The task is called twice and retry resolves with 'ok' on every run

**Rationale:** Cause: the test sleeps a fixed 40ms, but retry waits retryDelay(0) = 20ms plus Math.floor(Math.random()*40) of jitter, which is 20–59ms. Whenever the jitter goes above 20ms, the second call hasn't happened when the test checks for it. The probe failed 8 of 10 runs with 'called 1 times'. The fix waits for the condition itself and keeps both assertions.

### TC2: stops telling a handler once it unsubscribes

*unit · vitest · regression · high priority* — covers AC2

**Steps**
1. In 'tells every handler subscribed to the topic', register each subscription's stop function with onTestFinished so the handlers are removed even when that test fails
2. Subscribe a handler, unsubscribe it, publish on 'records'
3. Assert publish returns 0 and the handler wasn't called

**Expected:** Passes in every shuffled order

**Rationale:** Cause: order dependence through shared module state. src/subscribers.js keeps one handler Map for the whole process, and 'tells every handler subscribed to the topic' subscribes two handlers to 'records' and never removes them. When that test runs first (shuffled order), publish('records') returns 2. The probe failed 6 of 10 runs with 'expected 2 to be +0'. The fix makes every test remove the subscriptions it creates.

### TC3: resolves with the ids in the order of the records

*unit · vitest · regression · high priority* — covers AC3

**Steps**
1. Keep the saveAll test and its assertion, and mark it it.skip with a comment naming the cause
2. record_defect against test/bulk.test.js, then file_issue

**Expected:** The test no longer runs, so it can't fail builds at random. The defect is recorded and an issue is filed

**Rationale:** Cause in application code: saveAll in src/bulk.js runs every save at once and does ids.push(await client.save(record)) inside each callback. Ids therefore land in the order the saves complete, and the records client's latency is random. This breaks the documented record-order guarantee. The probe failed 5 of 10 runs with ['second','first']. A change to the test can't fix this without hiding the bug.

## Assumptions

- subscribers.js keeps one handler list for the whole process by design (its doc comment says so), so each test has to remove its own subscriptions.
- bulk.js documents that saveAll returns ids in record order, so the out-of-order result is an application defect, not a wrong test.
