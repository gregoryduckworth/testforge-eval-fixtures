# Test strategy: ROOM-7 Book meeting rooms

Revision 1 · generated by TestForge

## Summary

createBookings() checks room, owner, start alignment (UTC half hour) and length (30–240 min, steps of 30), refuses overlapping bookings of the same room, lists a room's bookings by start time, and lets only the owner cancel. Unit tests with vitest against memoryStore() prove each rule and the refusal (BookingError + its message) beside each accepted path, including boundaries and back-to-back bookings, plus simultaneous requests for one slot.

## Scope

**In scope**
- createBookings().book/list/cancel with memoryStore()
- BookingError type and message for each refusal
- Boundaries: 30/240 minutes, start alignment incl. seconds and non-UTC offsets, adjacent bookings
- Simultaneous booking requests for the same slot

**Out of scope**
- The app's database-backed BookingStore (not in the repository)

## Risks

| Risk | Impact | Mitigation |

| Validation boundaries (30/240 minutes, half-hour alignment) off by one | high | Accepted and refused rows on each side of each boundary |
| Overlap check too strict (rejects back-to-back) or too loose (misses containment) | high | Rows for each overlap shape plus adjacent bookings both ways and other rooms |
| Check-then-add race lets simultaneous requests double-book a room | medium | TC11 sends two requests at once |
| Cancellation by another person deletes a booking | high | TC15 checks refusal and that the booking stays listed |

## Assumptions

- Tests use memoryStore(), as the README says tests do; a fresh createBookings() per test keeps them independent.
- Messages are asserted exactly: they are written by the module under test and AC1 requires the error to say why.
- Q1 (pending): AC2 covers simultaneous requests too; if two simultaneous bookings of the same slot both succeed, the test is kept as expected-to-fail and a defect is recorded.
- The existing at() helper in test/bookings.test.ts moves to test/support/time.ts so both specs import it.
