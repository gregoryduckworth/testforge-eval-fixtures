# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the catalogue by a case-insensitive substring `q`, pages with `limit` (default DEFAULT_LIMIT=20, capped at MAX_LIMIT=50) and `offset` (default 0), and returns { total, items }. Non-whole limit/offset or limit < 1 return 400. Tests run the real app in-process on an OS-chosen port against the fixed 120-product catalogue.

## Scope

**In scope**
- GET /products search by q
- limit/offset paging, total, limit cap
- 400 validation of limit and offset

**Out of scope**
- GET /products/:id and POST /orders (not in the ticket)
- UI search box

## Acceptance criteria coverage

| AC | Criterion | Test cases |

| AC3 | A non-whole-number limit or offset, or limit below 1, returns 400 | TC8, TC9, TC10 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Search becomes case-sensitive or prefix-only | high | TC1 uses mixed case and a mid-name substring |
| total reports the page size instead of all matches | high | TC5 checks total larger than page |
| Uncapped limit lets clients dump the whole catalogue | medium | TC6 |
| Malformed paging params cause 500 or silent defaults | medium | TC8-TC10 |

## Environment

No external services; the app starts in-process on an OS-chosen port. Runs under the existing `npm test` (vitest run).

## Assumptions

- The real app runs in-process via createApp() on port 0; nothing is faked. The catalogue is the static PRODUCTS array (120 items, names '<Name> 1..15'); GET /products never mutates it, so tests share it read-only.
- Results are in catalogue order (id ascending), so a page is checked by ids.
- Expected counts come from the documented catalogue (e.g. 15 Teapots); DEFAULT_LIMIT, MAX_LIMIT and PRODUCTS are imported from src rather than copied.
