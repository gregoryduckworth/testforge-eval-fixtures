# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue (120 products) by a case-insensitive name substring `q`, returns one page selected by `limit` (default 20, capped at MAX_LIMIT) and `offset`, with `total` = number of matches, and refuses non-whole limit/offset or limit < 1 with 400. Integration tests start the real app in-process on port 0 and call the endpoint over HTTP.

## Scope

**In scope**
- GET /products query parameters q, limit, offset
- Response shape { total, items }
- 400 refusals for invalid limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- The shop UI's search box

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | q matches products whose name contains it, in any case; without q every product is listed. | TC1, TC2, TC3 |
| AC2 | Results come a page at a time with limit and offset, the response gives the total number of matches, and large limits are capped at MAX_LIMIT (50). | TC4, TC5, TC6, TC7, TC10 |
| AC3 | A limit or offset that isn't a whole number, or a limit below 1, is refused with 400. | TC8, TC9, TC10, TC11 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Search is case-sensitive or matches only a prefix | high | TC1 uses mixed-case q matching mid-name and asserts the full match count |
| total reports the page size instead of all matches | high | TC5 asserts total larger than the page |
| Uncapped limit lets clients pull the whole catalogue | medium | TC6 asserts a huge limit returns exactly MAX_LIMIT items |
| Bad input yields 500 or silently defaults | medium | TC8, TC9, TC11 assert 400 for each invalid shape |

## Test case detail

### TC1: matches products whose name contains q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- App running in-process

**Steps**
1. GET /products?q=TeA&limit=50

**Expected:** 200, total 30, 30 items each with a name containing 'tea' ignoring case, including 'Teapot 1' and 'Tea strainer 1'

**Test data:** q=TeA (matches the 15 Teapots and 15 Tea strainers)

**Rationale:** Core search behaviour: substring and case-insensitivity

- The real app runs in-process (createApp on port 0); nothing is faked. The catalogue is the fixed PRODUCTS list from src/catalogue.js, which GET /products never changes.
- Server start/stop moves into a shared helper test/helpers/server.js used by both test/products.test.js and the new spec.
