# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the catalogue by a case-insensitive substring `q`, pages with `limit` (default DEFAULT_LIMIT=20, capped at MAX_LIMIT=50) and `offset` (default 0), returns { total, items }, and refuses non-whole limit/offset or limit < 1 with 400. Tests start the real app in-process on an OS-chosen port, like the existing test/products.test.js, and assert against the fixed 120-product catalogue.

## Scope

**In scope**
- GET /products search by q
- limit/offset paging and total
- limit cap
- 400 validation of limit and offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- The shop's search box UI (not in this repo)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | `q` returns only products whose name contains it case-insensitively; without `q` every product is listed. | TC1, TC2, TC3, TC5 |
| AC2 | Results are paged by `limit` and `offset`, the response's `total` is the number of all matches, and limits above the maximum are capped. | TC2, TC4, TC5, TC6, TC7 |
| AC3 | A `limit` or `offset` that isn't a whole number, or a `limit` below 1, gets 400. | TC8, TC9, TC10 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Search is case-sensitive or matches only prefixes, so shoppers miss products | high | TC1 uses an upper-case q that matches mid-name and prefix names; TC3 checks no-match gives empty. |
| total reports page size instead of all matches, breaking pagination UI | high | TC4/TC5/TC10 assert total independently of page size. |
| Unbounded limit lets clients dump the whole catalogue | medium | TC6 requests 1000 and expects MAX_LIMIT items. |
| Malformed paging params produce NaN slices or 500s | medium | TC7-TC9 cover non-numeric, decimal, negative and zero values. |

## Test case detail

### TC1: matches q anywhere in the name regardless of case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- app listening on an OS-chosen port

**Steps**
1. GET /products?q=TEA&limit=50

**Expected:** 200, total 30 (15 Teapot + 15 Tea strainer), every item name contains 'tea' case-insensitively, and both 'Teapot 1' and 'Tea strainer 1' are present

**Test data:** q=TEA

**Rationale:** Core search behaviour and case-insensitivity

### TC2: lists every product when q is absent

*integration · vitest · positive · high priority* — covers AC1, AC2

**Steps**
1. GET /products

**Expected:** 200, total equals PRODUCTS.length (120), items are the first DEFAULT_LIMIT products in order

**Rationale:** No-q path and default page

## Environment

No services or env vars; the app is started in-process on port 0 by the test file. Runs under the existing `npm test` (vitest run).

## Assumptions

- The real app runs in-process via createApp() on port 0 (OS-chosen); nothing is faked.
- The cap is the exported MAX_LIMIT (50) and the default page size DEFAULT_LIMIT (20); tests import them rather than hard-coding.
- The catalogue is the fixed PRODUCTS list from src/catalogue.js (120 products, 'Name N' for N 1-15); search tests assert on known names/counts from it.
- Negative numbers and decimals count as 'not a whole number'.

## Open questions

- Should an empty `limit=` / `offset=` be treated as absent (default) or refused? The code refuses it with 400; tests don't pin it.
- Should `q` be trimmed of surrounding whitespace? The code does not trim; not tested.
