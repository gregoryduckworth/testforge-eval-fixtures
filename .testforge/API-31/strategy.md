# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the in-memory catalogue by a case-insensitive name substring `q`, pages it with `limit` (default 20, capped at MAX_LIMIT=50) and `offset` (default 0), returns { total, items }, and rejects non-whole limit/offset or limit < 1 with 400. The tests start the real app on an OS-chosen port, as test/products.test.js does, and prove each rule through HTTP.

## Scope

**In scope**
- GET /products: q filtering, listing without q, limit/offset paging, total, limit cap, 400 validation

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- Updating the README's stale 'up to 100' (reviewer said to leave it)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | q matches products whose name contains it, in any case; without q every product is listed. | TC1, TC2, TC3, TC5 |
| AC2 | Results are paged by limit and offset, the response gives the total number of matches, and limits above the cap (50) are capped. | TC4, TC5, TC6, TC7 |
| AC3 | A limit or offset that isn't a whole number, or a limit below 1, is refused with 400. | TC8, TC9, TC10 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Case-insensitive matching could break for mixed-case queries | high | TC1 uses a mixed-case q and checks the exact total and names |
| Cap bypass lets clients request the whole catalogue | medium | TC6 asks for more than the cap and asserts exactly MAX_LIMIT items |
| Loose number parsing accepts decimals or negatives | medium | TC8–TC10 check 400 for each invalid form |
