# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by a case-insensitive name substring `q`, pages the results with `limit` (default 20, capped at MAX_LIMIT) and `offset`, and returns `{ total, items }`. It refuses a limit or offset that isn't a whole number, and a limit below 1, with a 400. The tests start the real app with createApp() on an OS-chosen port and check the responses against the real catalogue (PRODUCTS).

## Scope

**In scope**
- GET /products: q filtering, listing without q, limit/offset paging, total count, the limit cap, 400 validation

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- The search box UI (no UI exists in this repo)

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A case-sensitive or prefix-only match would miss products whose name contains the query | high | TC1 sends a mixed-case query that matches the middle of names and asserts the exact set of names returned |
| total could report the page size instead of the number of matches | high | TC3 and TC4 check total against the full match count while the page is smaller |
| Without a working cap, a huge limit could return the whole catalogue | medium | TC5 asks for limit=1000 and expects exactly MAX_LIMIT items |
| Bad paging input could return 200 or 500 instead of 400 | medium | TC6–TC8 cover a non-integer, a non-numeric and a negative value, and a limit of 0 |

## Test case detail

### TC1: matches products whose name contains q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- App listening on an ephemeral port

**Steps**
1. GET /products?q=tEA&limit=MAX_LIMIT

**Expected:** 200; total is 30, and items are exactly the Teapot and Tea strainer products, by id; every item's name contains 'tea' when lower-cased

**Test data:** q=tEA (matches 'Teapot n' and 'Tea strainer n', 15 of each)

**Rationale:** Core search behaviour: mixed case, and a match that isn't only at the start of the full name

## Environment

## Assumptions

- The cap is the code's exported MAX_LIMIT (50 today). The README says 100, so I asked as Q1. The tests import MAX_LIMIT and DEFAULT_LIMIT instead of hard-coding them.
- The tests run the real app in-process, nothing faked, on port 0, the same way test/products.test.js does. The expected values come from filtering the imported PRODUCTS, so the tests don't reimplement the app's logic: each one asserts concrete ids or names for the data it queries.
- Results are ordered by id, as the README says, and pages are contiguous slices of that order.
- A negative offset or limit (e.g. -1) counts as 'not a whole number', and the code refuses it with 400.
