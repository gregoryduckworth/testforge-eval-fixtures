# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit`/`offset` (default limit 20, capped at MAX_LIMIT), returns `{ total, items }`, and refuses non-whole-number limit/offset or limit < 1 with 400. Integration tests start the real app on an ephemeral port (as the existing test does) and assert exact results computed from the exported PRODUCTS catalogue and constants.

## Scope

**In scope**
- GET /products search by q
- paging with limit/offset and total
- limit cap
- 400 validation of limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not in ticket)
- The shop UI search box (not in this repo)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | q returns exactly the products whose name contains q case-insensitively; without q every product is listed. | TC1, TC2 |
| AC2 | Results are paged by limit and offset, the response's total is the number of all matches, and limits above the cap return at most the cap. | TC3, TC4, TC5 |
| AC3 | A limit or offset that isn't a whole number, or a limit below 1, gets 400. | TC6, TC7 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Cap differs between README (100) and code (50) | medium | TC5 asserts the cap from the exported MAX_LIMIT; question raised |
| Case-sensitive matching would break search for typed lowercase/uppercase queries | high | TC1 uses mixed case query and checks exact matching ids |
| total reported as page size rather than match count | high | TC3 checks total against full match count while page is smaller |

## Test case detail

### TC1: matches names containing q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- app listening on port 0

**Steps**
1. GET /products?q=tEA&limit=50

**Expected:** 200; items are exactly the PRODUCTS whose lowercased name includes 'tea' (Teapot n, Tea strainer n), in id order; total equals that count (30)

**Test data:** q=tEA

**Rationale:** Core search and case-insensitivity

## Environment

No services; the app starts in-process on an OS-chosen port. Runs under the existing `npm test` (vitest run).

## Assumptions

- The cap is the code's MAX_LIMIT (50), not the README's 100 (asked as Q1); tests import MAX_LIMIT and DEFAULT_LIMIT from src/app.js.
- The real app runs in-process via createApp() on port 0; nothing is faked. The catalogue is static for names, so expected results are derived from the exported PRODUCTS array.
- Items keep catalogue (id) order, per README 'by id'.
