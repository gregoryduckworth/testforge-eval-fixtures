# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by case-insensitive name substring `q`, pages with `limit` (default 20, capped at MAX_LIMIT=50) and `offset` (default 0), returns { total, items }, and refuses non-whole-number limit/offset or limit < 1 with 400. Integration tests start the real app in-process on port 0 and call it over HTTP, asserting exact results computed from the imported catalogue and constants.

## Scope

**In scope**
- GET /products search by q, paging, total, cap and 400 validation
- Shared in-process server helper test/helpers/server.js, reused by test/products.test.js

**Out of scope**
- GET /products/:id and POST /orders behaviour (already covered/not in ticket)
- Updating the stale README (not a test file)

## Acceptance criteria coverage

| AC | Criterion | Test cases |

| AC3 | A non-whole-number `limit` or `offset`, or a `limit` below 1, is refused with 400. | TC10, TC11, TC12 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Cap value disagreement between README (100) and code (50) | medium | Tests import MAX_LIMIT and assert exactly MAX_LIMIT items for limit above it and at it. |

## Environment

No external services. Vitest runs via `npm test`; the app is started in-process on an OS-chosen port by a shared helper test/helpers/server.js.

## Assumptions

- The cap is MAX_LIMIT = 50 from src/app.js; the README's 'up to 100' is stale (confirmed by a person in earlier runs, re-asked this run).
- The real app runs in-process for every test; nothing is faked. The catalogue is static (120 products, read-only for GET), so tests can import PRODUCTS, DEFAULT_LIMIT and MAX_LIMIT and compute exact expectations.
- Items come in catalogue (id) order, as the README states.
