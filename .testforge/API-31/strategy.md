# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters products by a case-insensitive substring of the name (`q`), returns one page at a time using `limit` (default DEFAULT_LIMIT=20, capped at MAX_LIMIT=50) and `offset`, includes `total`, the number of matches, and refuses with 400 a limit or offset that isn't a whole number, or a limit below 1. The tests are Vitest integration tests that start the real server in-process on an OS-chosen port, as test/products.test.js already does, and check search, paging, the cap and the refusals against the fixed in-memory catalogue.

## Scope

**In scope**
- GET /products query handling: q, limit, offset, total, the limit cap and the 400 refusals

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- The search box UI (the repo has no UI)

## Acceptance criteria coverage

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Paging overlaps or skips results, or total counts the page rather than all matches | high | TC4 checks the exact ids of a page in the middle of the results and that total stays at 30. TC7 checks an offset past the end. |
| An unbounded limit lets a client pull the whole catalogue | medium | TC6 asserts that the page size equals the imported MAX_LIMIT. |
| Malformed paging values are accepted silently | medium | TC8 to TC10 cover non-numeric, fractional, negative and zero values. |

## Test case detail

### TC1: matches product names containing q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- Server started in-process on port 0

**Steps**
1. GET /products?q=tEA&limit=50

**Expected:** 200. total is 30, and items are exactly the Teapot 1-15 and Tea strainer 1-15 products, in id order (each name matches ^(Teapot|Tea strainer) \d+$, 30 items).

**Test data:** q=tEA

**Rationale:** This is the core search behaviour. The mixed-case query proves case-insensitivity.

### TC2: lists every product when q is absent

*integration · vitest · positive · high priority* — covers AC1

**Preconditions**
- Server started

**Steps**
1. GET /products

**Expected:** 200. total equals PRODUCTS.length (120), and items are ids 1..DEFAULT_LIMIT in order.

**Rationale:** With no query, the whole catalogue is listed. This also covers the default page size.

### TC3: returns no items and a total of 0 when nothing matches q

*integration · vitest · negative · medium priority* — covers AC1

**Preconditions**
- Server started

**Steps**
1. GET /products?q=blender

**Expected:** 200 with { total: 0, items: [] }

**Test data:** q=blender

**Rationale:** The search can also find nothing. This case covers that.

### TC4: returns the requested page of matches with the total of all matches

*integration · vitest · positive · critical priority* — covers AC2

**Preconditions**
- Server started

**Steps**
1. GET /products?q=tea&limit=5&offset=5

**Expected:** 200. total is 30, and items are the 6th to 10th tea matches by id (ids 15, 19, 23, 27, 31: Tea strainer 2, Teapot 3, Tea strainer 3, Teapot 4, Tea strainer 4).

**Test data:** q=tea, limit=5, offset=5

**Rationale:** Proves offset and limit work together on the filtered results, and that total counts all matches, not just the page.

### TC5: caps a large limit at the maximum page size

*integration · vitest · edge · high priority* — covers AC2

**Preconditions**
- Server started

**Steps**
1. GET /products?limit=1000

**Expected:** 200. items has MAX_LIMIT entries (ids 1..MAX_LIMIT), and total is 120.

**Test data:** limit=1000

**Rationale:** This case covers the ticket's 'large limits are capped' rule.

### TC6: returns a full page when limit equals the maximum

*integration · vitest · edge · medium priority* — covers AC2

**Preconditions**
- Server started

**Steps**
1. GET /products?limit=MAX_LIMIT, then GET /products?limit=MAX_LIMIT+1

**Expected:** Both responses are 200 with MAX_LIMIT items.

**Rationale:** Checks both sides of the cap boundary.

### TC7: returns no items but the full total when offset is past the last match

*integration · vitest · edge · medium priority* — covers AC2

**Preconditions**
- Server started

**Steps**
1. GET /products?q=tea&offset=30

**Expected:** 200 with { total: 30, items: [] }

**Rationale:** Checks the paging boundary at the end of the results.

### TC8: refuses a limit that is not a whole number with 400

*integration · vitest · negative · high priority* — covers AC3

**Preconditions**

**Steps**
1. GET /products?limit=<v> for each of abc, 2.5, -1, 1e2, empty string

**Expected:** 400 for each value

**Test data:** abc, 2.5, -1, 1e2, ''

**Rationale:** Covers validation of limit.

### TC9: refuses a limit of 0 with 400 and accepts a limit of 1

*integration · vitest · edge · high priority* — covers AC3

**Preconditions**
- Server started

**Steps**
1. GET /products?limit=0
2. GET /products?limit=1

**Expected:** limit=0 gets 400. limit=1 gets 200 with exactly one item (id 1).

**Rationale:** Checks both sides of the lower bound on limit.

### TC10: refuses an offset that is not a whole number with 400

*integration · vitest · negative · high priority* — covers AC3

**Preconditions**
- Server started

**Steps**
1. GET /products?offset=<v> for each of abc, 1.5, -1, empty string
2. GET /products?offset=0

**Expected:** 400 for each invalid value. offset=0 gets 200.

**Test data:** abc, 1.5, -1, ''

**Rationale:** Covers validation of offset, with the valid boundary as a control.

## Environment

No external services. The tests start createApp() in-process with listen(0), like the existing test/products.test.js, and run under the existing `npm test` (vitest run).

## Assumptions

- The code's limit cap MAX_LIMIT=50 is correct and the README's 'up to 100' is out of date (asked as Q1). The tests import MAX_LIMIT and DEFAULT_LIMIT from src/app.js.
- Expected data comes from the fixed 120-product catalogue in src/catalogue.js (8 names x 15). For example, 'tea' matches the 15 Teapots and the 15 Tea strainers, 30 in all, in id order.
- No service is faked: the real HTTP server from createApp() runs in-process on port 0.
- An empty value (`limit=`) counts as not a whole number, and the code refuses it with 400.
