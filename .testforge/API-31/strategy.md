# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the catalogue by a case-insensitive name substring `q`, pages with `limit` (default DEFAULT_LIMIT=20, capped at MAX_LIMIT=50) and `offset` (default 0), returns {total, items}, and answers 400 when limit/offset aren't whole numbers (regex ^\d+$) or limit < 1. Tests start the real app in-process on an OS-chosen port, as the existing suite does, and prove search, paging, the cap and each refusal.

## Scope

**In scope**
- GET /products query parameters q, limit, offset
- Response shape {total, items}
- 400 refusals for bad limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- Shop search box UI (not in this repository)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | q returns only products whose name contains q, case-insensitively; without q every product is listed. | TC1, TC2, TC3, TC4, TC6 |
| AC2 | Results are paged with limit and offset, the response includes the total number of matches, and limits above the maximum are capped. | TC3, TC5, TC6, TC7, TC8 |
| AC3 | A limit or offset that isn't a whole number, or a limit below 1, is refused with status 400. | TC9, TC10, TC11 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Search is case-sensitive or matches only prefixes, so shoppers miss products | high | TC1 uses mixed case; TC2 matches a substring inside names |
| total reports the page size instead of all matches, breaking pagination UI | high | TC3, TC5, TC6, TC7 assert total independently of the page length |
| Unbounded limit lets a client fetch huge pages | medium | TC7 asserts the MAX_LIMIT cap |
| Malformed paging params cause 500s or silently wrong pages | medium | TC9-TC11 assert 400 for each kind of bad value |

## Environment

No external services. The app is started in-process with createApp().listen(0) per test file and closed in afterAll; the existing `npm test` (vitest run) picks up the new file.

## Assumptions

- The real app runs in-process via createApp() on port 0, nothing is faked; expectations are derived from the exported PRODUCTS catalogue, DEFAULT_LIMIT and MAX_LIMIT rather than hard-coded copies where possible.
- 'Capped' means a limit above MAX_LIMIT (50) returns MAX_LIMIT items with status 200, not a refusal, as the code does.
- A negative number or an empty value counts as 'not a whole number' and is refused with 400, as the code does; offset 0 is valid.
- Items are returned in catalogue order (by id), which the code does; paging assertions rely on it.
