# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters by case-insensitive name substring `q`, pages with `limit`/`offset` (limit default 20, capped at MAX_LIMIT), returns {total, items}, and refuses non-whole-number limit/offset or limit < 1 with 400. Integration tests against the real in-process server (createApp on port 0) over the fixed in-memory catalogue of 120 products prove each rule.

## Scope

**In scope**
- GET /products search by q
- paging with limit/offset and total
- limit cap
- 400 validation of limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- UI search box

## Acceptance criteria coverage

| AC | Criterion | Test cases |

| AC3 | A non-whole-number `limit` or `offset`, or a `limit` below 1, gets 400. | TC7, TC8, TC9, TC10 |

## Test case detail

### TC1: matches q against product names in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- app listening on an OS-chosen port

**Steps**
1. GET /products?q=tEaPoT&limit=50

**Expected:** 200; total 15; items' names are exactly 'Teapot 1'..'Teapot 15' in id order

**Test data:** q=tEaPoT

**Rationale:** Core search behaviour and case-insensitivity.

### TC2: matches q anywhere inside the name

*integration · vitest · edge · high priority* — covers AC1

**Preconditions**
- app listening

**Steps**
1. GET /products?q=STRAINER&limit=50

**Expected:** 200; total 15; every item name is 'Tea strainer N' (substring, not prefix)

**Test data:** q=STRAINER

**Rationale:** Proves 'contains', not 'starts with'.
