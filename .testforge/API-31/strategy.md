# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit`/`offset` (limit default 20, capped at MAX_LIMIT), returns { total, items }, and refuses non-whole limit/offset or limit < 1 with 400. Integration tests start the real app in-process on port 0 and call it over HTTP to prove search, paging, the cap and the refusals.

## Scope

**In scope**
- GET /products query parameters q, limit, offset
- Response shape { total, items } and status codes 200/400
- A shared in-process server helper for specs (test/helpers/server.js), adopted by the existing test/products.test.js

**Out of scope**
- GET /products/:id and POST /orders behaviour (not in the ticket)
- The shop's search box UI (not in this repo)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | q matches products whose name contains it, case-insensitively; without q every product is listed. | TC1, TC2, TC3 |
| AC2 | Results are paged with limit and offset, the response's total is the number of all matches, and limits above the maximum are capped. | TC4, TC5, TC6, TC11 |
| AC3 | A limit or offset that isn't a whole number, or a limit below 1, is refused with 400. | TC7, TC8, TC9, TC10 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Case-sensitive matching would break the search box for mixed-case input | high | TC1 searches with mixed case and asserts the exact matching set |
| total reflects the page instead of all matches, breaking pagination UI | high | TC5 asserts total 30 with a page of 5 |
| Uncapped limit lets clients pull the whole catalogue | medium | TC6 requests a limit far above MAX_LIMIT |
| Lenient parsing (2.5, -3, '') silently accepted | medium | TC7, TC8 and TC9 cover each invalid shape |

## Test case detail

### TC1: matches q against product names in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- App started in-process

**Steps**
1. GET /products?q=tEA&limit=50

**Expected:** 200, total 30, items are Teapot 1..15 and Tea strainer 1..15 (every name contains 'tea' ignoring case)

**Test data:** q=tEA

**Rationale:** Core search behaviour including case-insensitivity

### TC2: lists every product when q is absent

## Environment

No services: vitest starts the app in-process on an OS-chosen port via a shared helper test/helpers/server.js. Runs under the existing `npm test`.

## Assumptions

- The limit cap is MAX_LIMIT = 50 as the code says, not the README's 100 (asked as Q1; earlier runs were told the code is right). Tests import MAX_LIMIT and DEFAULT_LIMIT from src/app.js.
- The app runs for real in-process (createApp().listen(0)); nothing is faked. The catalogue is the fixed 120-product list in src/catalogue.js, which GET /products doesn't modify, so tests can share one server.
- Results are ordered by id (catalogue order), as the README says.

## Open questions

- README says limit goes up to 100, code caps at 50 (Q1). Tests follow the code; README should be fixed.
- Is a negative offset meant to be refused? The code refuses it (it isn't a whole number); tests assert that.
