# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit` (default 20, capped at MAX_LIMIT) and `offset`, and returns { total, items }. Tests start the real app in-process (as test/products.test.js does) and prove filtering, paging, total, the cap and the 400 refusals.

## Scope

**In scope**
- GET /products query filtering, paging, total, limit cap, validation of limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | `q` returns products whose name contains it case-insensitively; without `q` every product is listed. | TC1, TC2 |
| AC2 | `limit` and `offset` page the results, the response's `total` is the number of all matches, and limits above the maximum are capped. | TC3, TC4, TC5 |
| AC3 | A non-whole-number `limit` or `offset`, or a `limit` below 1, gets 400. | TC6, TC7, TC8 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Paging returns overlapping/missing items or a total that counts only the page | high | TC3/TC4 compare consecutive pages and total to the full filtered list |
| Unbounded limit lets clients pull the whole catalogue | medium | TC5 asserts exactly MAX_LIMIT items for a larger limit |
| Malformed paging values silently accepted (NaN slice returns empty/everything) | medium | TC6-TC8 assert 400 for decimals, negatives, non-numbers and limit 0 |

## Test case detail

### TC1: matches names containing q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- app listening on an OS-chosen port

**Steps**
1. GET /products?q=tEA&limit=50

**Expected:** 200; total equals the number of catalogue products whose lowercased name contains 'tea' (Teapot, Tea strainer = 30); items are exactly those products in id order

**Test data:** q=tEA

**Rationale:** Core search behaviour including case-insensitivity

### TC2: lists every product when q is absent

*integration · vitest · positive · high priority* — covers AC1

**Preconditions**
- app listening

**Steps**
1. GET /products

**Expected:** 200; total equals PRODUCTS.length (120); items are the first DEFAULT_LIMIT products

**Rationale:** Default listing and default page size

### TC3: returns the page at offset with the total of all matches

*integration · vitest · positive · critical priority* — covers AC2

**Preconditions**
- app listening

**Steps**
1. GET /products?q=kettle&limit=4&offset=0
2. GET /products?q=kettle&limit=4&offset=4

**Expected:** Both have total 15; first items are kettles 1-4, second kettles 5-8, matching slices of the expected matches

**Test data:** q=kettle

**Rationale:** Paging correctness and total independent of page

### TC4: returns no items for an offset past the last match

*integration · vitest · edge · medium priority* — covers AC2

**Steps**

## Environment

No services; the app starts in-process with createApp().listen(0). Run with `npm test`.

## Assumptions

- The code's cap MAX_LIMIT = 50 is correct, not the README's 100 (asked as Q1); tests import MAX_LIMIT and DEFAULT_LIMIT from src/app.js.
- The app runs for real in-process on an OS-chosen port; nothing is faked. Expected matches are computed from the exported PRODUCTS catalogue (fixed data), not hard-coded beyond what the catalogue defines.
- Results are in catalogue (id) order, as the README says, so pages can be compared to slices of the expected matches.
