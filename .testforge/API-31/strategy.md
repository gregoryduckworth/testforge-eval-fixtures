# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit`/`offset` (limit capped at MAX_LIMIT=50, default DEFAULT_LIMIT=20), returns `{ total, items }`, and rejects non-whole-number limit/offset or limit < 1 with 400. Tests start the real app in-process on an OS-chosen port (as the existing suite does) and assert against the real catalogue imported from src/catalogue.js.

## Scope

**In scope**
- Search by q (case-insensitive substring of name)
- Listing without q
- limit/offset paging and total
- Limit cap
- 400 for invalid limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- The shop's search box UI (not in this repository)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | `q` returns only products whose name contains it, case-insensitively; without `q` every product is matched. | TC1, TC2 |
| AC2 | Results are paged by `limit` and `offset`, the response includes `total` (number of all matches), and limits above the maximum are capped. | TC3, TC4, TC5, TC8 |
| AC3 | A non-whole-number `limit` or `offset`, or a `limit` below 1, gets 400. | TC6, TC7, TC8 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Search is case-sensitive or matches on other fields, so shoppers miss products | high | TC1 searches with mixed/upper case and asserts the exact set of matching ids |
| total reflects the page length instead of all matches, breaking pagination UI | high | TC3/TC4 assert total stays the full match count while items are a slice |
| Uncapped limit lets clients pull the whole catalogue | medium | TC5 asserts a huge limit returns exactly MAX_LIMIT items |
| Bad paging params produce 500s or silently wrong pages | medium | TC6–TC8 assert 400 for each invalid form |

## Environment

No external services. The real app is started in-process with createApp().listen(0) per test file and closed afterwards. Runs under the existing `npm test` (vitest run).

## Assumptions

- The real app runs in-process via createApp() on port 0; nothing is faked. Expected data is derived from the exported PRODUCTS, DEFAULT_LIMIT and MAX_LIMIT, so it follows the catalogue.
- Results are in catalogue order (the handler filters PRODUCTS without sorting), so page contents can be asserted exactly.
- `total` is the count of all matches, independent of limit/offset.
- Negative numbers (e.g. offset=-1) count as not a whole number and get 400, as the handler's /^\d+$/ check does.
