# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the in-memory catalogue by case-insensitive name substring `q`, pages with `limit` (default 20, capped at MAX_LIMIT = 50) and `offset` (default 0), returns `{ total, items }`, and refuses non-whole-number limit/offset or limit < 1 with 400. Integration tests start the real app in-process on port 0 and call it with fetch, proving filtering, paging, total, capping and refusals.

## Scope

**In scope**
- GET /products query parameters q, limit, offset
- Response shape { total, items } and 400 refusals

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- Updating the stale README limit (docs, not tests)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | `q` returns products whose name contains it case-insensitively; without `q` every product is listed. | TC1, TC2, TC3 |
| AC2 | Results are paged by `limit` and `offset`, the response's `total` is the number of all matches, and limits above MAX_LIMIT are capped to MAX_LIMIT. | TC4, TC5, TC6, TC7 |
| AC3 | A `limit` or `offset` that isn't a whole number, or a `limit` below 1, is refused with 400. | TC7, TC8, TC9, TC10 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Search is case-sensitive or matches only prefixes, so the shop search misses products | high | TC1 uses a mixed-case query matching mid-name and asserts exact total and names |
| total reports page size instead of all matches, breaking pagination UI | high | TC4/TC5/TC7 assert total differs from page length |
| Uncapped limit lets clients dump the whole catalogue | medium | TC6 asks for MAX_LIMIT+1 and asserts exactly MAX_LIMIT items |
| Bad paging input gives 200 with odd slices instead of 400 | medium | TC9-TC11 check each malformed value and limit=0 |

### TC1: matches names containing q in any case

*integration · vitest · positive · critical priority* — covers AC1

## Environment

No external services; the app runs in-process on an OS-chosen port via test/helpers/server.js. Runs under the existing `npm test` (vitest run).

## Assumptions

- The cap is MAX_LIMIT = 50 as in src/app.js; the README's 'up to 100' is stale (confirmed by a person in earlier runs on this ticket). Tests import MAX_LIMIT and DEFAULT_LIMIT rather than hard-coding them.
- The app runs for real in-process (createApp().listen(0)); nothing is faked. The catalogue is the fixed 120-product list in src/catalogue.js, which GET /products only reads, so tests share it safely.
- Server start/stop moves into a shared helper test/helpers/server.js used by both test/products.test.js and the new spec, instead of copying the setup.
- Results come in catalogue (id) order, as the code filters PRODUCTS in place.
