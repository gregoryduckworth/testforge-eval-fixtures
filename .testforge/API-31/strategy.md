# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit`/`offset` (default 20, capped at MAX_LIMIT), returns `{ total, items }`, and refuses non-whole-number limit/offset or limit < 1 with 400. Tests start the real app in-process on an OS-chosen port (as the existing spec does) and assert against expectations derived from the exported PRODUCTS catalogue and MAX_LIMIT/DEFAULT_LIMIT constants.

## Scope

**In scope**
- GET /products search by q (case-insensitive substring, no q lists all)
- Paging with limit/offset, total count, default limit, cap on large limits
- 400 for non-whole-number limit/offset and limit below 1

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)

## Acceptance criteria coverage

| AC | Criterion | Test cases |

| AC2 | Results are paged by `limit` and `offset`, the response's `total` is the number of matches regardless of paging, and a limit above the cap returns at most the cap. | TC4, TC5, TC6 |
| AC3 | A `limit` or `offset` that isn't a whole number, or a `limit` below 1, gets 400. | TC7, TC8, TC9, TC10 |

## Risks

| Risk | Impact | Mitigation |

| Lax validation (parseInt-style) would accept '1.5' or '10abc' | medium | TC6-TC8 cover decimal, non-numeric, negative and zero values |
