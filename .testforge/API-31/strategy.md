# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by a case-insensitive name substring `q`, pages results with `limit` (default 20, capped at MAX_LIMIT = 50) and `offset`, and returns `{ total, items }`; non-whole `limit`/`offset` or `limit` < 1 get 400. Integration tests start the real http server on an OS-chosen port (as the existing test does) and assert on the fixed 120-product catalogue.

## Scope

**In scope**
- GET /products search by q
- paging with limit/offset and total
- limit cap
- 400 validation of limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- the search box UI (no UI in this repo)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | `q` matches products whose name contains it, in any case; without `q` every product is listed. | TC1, TC2, TC3 |
| AC2 | Results are paged with `limit` and `offset`, the response's `total` is the number of matches, and limits above the cap (50) are capped. | TC4, TC5, TC6 |
| AC3 | A `limit` or `offset` that isn't a whole number, or a `limit` below 1, gets 400. | TC7, TC8, TC9 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Cap drifts from the documented value (README already disagrees) | medium | TC6 asserts the 50 cap and imports MAX_LIMIT |
| Lenient parsing (e.g. Number('2.5') or '-1') lets bad paging through | medium | TC7-TC9 cover fractional, negative, non-numeric and zero values |
| Case-sensitive matching would miss products | high | TC1 searches in upper case |

## Test case detail

### TC1: matches names containing q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- app listening on a random port

**Steps**
1. GET /products?q=TEA&limit=50

**Expected:** 200, total 30, items are exactly the 15 Teapot and 15 Tea strainer products (every name contains 'tea' case-insensitively)

**Test data:** q=TEA

**Rationale:** Core search behaviour and case-insensitivity

### TC2: lists every product when q is absent

*integration · vitest · positive · high priority* — covers AC1

**Preconditions**
- app listening

**Steps**
1. GET /products

**Expected:** 200, total 120, items are ids 1-20 (default limit)

**Rationale:** No-q path lists all

### TC3: returns no items and total 0 when nothing matches

## Environment

No external services; the test starts the app in-process on port 0. Runs under the existing `npm test` (vitest run).

## Assumptions

- The cap is 50, as the code's MAX_LIMIT says (confirmed by the reviewer in Q1); the README's 'up to 100' is stale and is left unchanged per the reviewer.
- Tests run the real app in-process via createApp() on port 0; nothing is faked. The catalogue (src/catalogue.js) is fixed, 120 products, 15 per name, so expected totals are known; orders only change stock, not names.
- Results are in id order (README: 'by id'), so pages can be asserted by id.
