# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit` (default 20, capped at MAX_LIMIT) and `offset`, returns { total, items }, and refuses non-whole or limit<1 values with 400. Integration tests start the real http server on an OS-chosen port (as test/products.test.js does) and assert search, paging, total, the cap and the refusals.

## Scope

**In scope**
- GET /products search by q (case-insensitive substring)
- Listing without q
- limit/offset paging, total, default and capped limit
- 400 refusals for invalid limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)

## Acceptance criteria coverage

| AC | Criterion | Test cases |

| AC3 | A limit or offset that isn't a whole number, or a limit below 1, is refused with 400. | TC8, TC9 |

## Risks

| Risk | Impact | Mitigation |

## Assumptions

- The code's cap MAX_LIMIT = 50 is correct and the README's 'up to 100' is stale (asked as Q1); tests import MAX_LIMIT and DEFAULT_LIMIT from src/app.js rather than hardcoding.
- Expected matches are derived from the exported PRODUCTS catalogue (src/catalogue.js) with the same filter in the test for counts only where needed; concrete names/ids are asserted where the catalogue is fixed (e.g. 'kettle' matches the 15 Kettle products).
- The server runs for real in-process on port 0; nothing is faked. GET /products doesn't mutate state, so sharing one server per file is safe.
