# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit`/`offset` (limit defaults to 20, capped at MAX_LIMIT), returns `{ total, items }`, and refuses non-whole-number limit/offset or limit < 1 with 400. The tests start the real app on an OS-chosen port (as the existing spec does) and check search, paging, the cap and the refusals over HTTP.

## Scope

**In scope**
- GET /products query parameters q, limit, offset
- total count and page contents
- the limit cap
- 400 validation of limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | q returns exactly the products whose name contains it, case-insensitively; without q every product is listed. | TC1, TC2, TC3 |
| AC2 | limit and offset select a page of the matches, the response's total is the number of all matches, and limits above the maximum are capped. | TC4, TC5, TC6 |
| AC3 | limit or offset that isn't a whole number, or limit below 1, gets 400. | TC7, TC8 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Case-sensitive matching would miss products when users type in a different case | high | TC2 searches in upper case and checks the same matches as lower case |
| total reports the page size instead of all matches, breaking pagination UI | high | TC4 checks total stays 15 while the page holds 5 |
| Unbounded limit lets a client fetch the whole catalogue | medium | TC5 asks for 1000 and expects exactly MAX_LIMIT items |
| Bad paging values silently accepted | medium | TC6 table of invalid values each expecting 400 |

## Environment

No external services. The app is started in-process on an OS-chosen port; runs with the existing `npm test`.

## Assumptions

- The cap is the code's MAX_LIMIT = 50, not the README's 100 (asked as Q1); tests import MAX_LIMIT and also check that 50 items come back.
- The real app runs in-process via createApp() on port 0; nothing is faked. The catalogue is the fixed 120-product PRODUCTS list (names like 'Kettle 1'..'Kettle 15'), which the GET endpoint doesn't modify.
- Items come back in catalogue (id) order, as the README says.
- A negative offset ('-1') counts as not a whole number and is refused, as the code does.
