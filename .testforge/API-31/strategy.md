# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by a case-insensitive name substring `q`, pages with `limit` (default 20, capped at MAX_LIMIT) and `offset`, returns { total, items }, and refuses non-whole limit/offset or limit < 1 with 400. Integration tests start the real http server in-process (as the existing test does) and assert on responses.

## Scope

**In scope**
- GET /products search by q
- paging with limit/offset and total
- limit cap
- 400 validation of limit and offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- the search box UI (not in this repository)

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Search is case-sensitive or matches prefixes only | high | TC1 uses mixed case on a substring in the middle of names; TC2 no-q full list; TC3 no match |
| Paging off by one or total reflecting the page rather than all matches | high | TC4 checks exact ids of a middle page and total; TC5 offset past the end |
| Large limits not capped, allowing huge responses | medium | TC6 |
| Bad paging input accepted or crashing | medium | TC7-TC9 parameterised 400 cases, TC10 boundary limit=1 accepted |

### TC1: matches names containing q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- app listening on an OS-chosen port

**Steps**

**Test data:** q=eaPO (mixed case, mid-word substring of 'Teapot')

**Rationale:** Core search behaviour, case and substring together

## Environment

No external services. Tests start createApp() in-process on port 0 (OS-chosen), like test/products.test.js, and run with `npm test` (vitest run).

## Assumptions

- The code's cap (MAX_LIMIT = 50 in src/app.js) is right, not the README's 'up to 100' (asked as Q1); tests import MAX_LIMIT and DEFAULT_LIMIT rather than hard-coding them.
- The catalogue is the fixed in-memory PRODUCTS list from src/catalogue.js (120 products, 15 per name); tests import PRODUCTS for the full count and rely on its names for search data. No service is faked: the real app runs in-process on an OS-chosen port.
- Results are ordered by id (catalogue order), as the README says.
- An empty `limit=` or `offset=` counts as not a whole number and is refused with 400, as the code does.
