# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products (src/app.js listProducts) filters the 120-product catalogue by a case-insensitive name substring `q`, pages with `limit` (default DEFAULT_LIMIT=20, capped at MAX_LIMIT=50) and `offset` (default 0), returns `{ total, items }`, and refuses non-whole-number limit/offset or limit < 1 with 400. Tests start the real app in-process on an OS-chosen port and assert on the HTTP responses.

## Scope

**In scope**
- GET /products query `q`, `limit`, `offset` behaviour and the `total`/`items` response
- 400 validation of limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- The shop's search box UI (not in this repository)

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | `q` returns only products whose name contains it, case-insensitively; without `q` every product is matched. | TC1, TC2, TC3 |
| AC2 | Results are paged by `limit` and `offset`, the response's `total` is the number of all matches, and limits above the maximum are capped. | TC2, TC4, TC5, TC6, TC7 |
| AC3 | A `limit` or `offset` that isn't a whole number, or a `limit` below 1, is refused with 400. | TC7, TC8, TC9 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Case-insensitive match broken (e.g. only lowercasing one side), so the search box misses products | high | TC1 searches with upper-case and mixed-case q and checks exact total and names |
| total reflects the page size instead of all matches, breaking pagination UI | high | TC3/TC4 assert total stays the match count while items is a slice |
| Unbounded limit lets a client fetch the whole catalogue | medium | TC5 asserts limit above MAX_LIMIT returns exactly MAX_LIMIT items |
| Invalid paging input yields 500 or silently odd results | medium | TC7-TC9 assert 400 for each refused shape |

## Environment

No external services; the app starts in-process on port 0. Runs under the existing `npm test` (vitest run).

## Assumptions

- The real app runs in-process via createApp() on port 0, as test/products.test.js does; nothing is faked.
- The catalogue is the fixed PRODUCTS list from src/catalogue.js (120 items, names like 'Kettle 1'..'Kettle 15'); expected names/counts are written from it, and DEFAULT_LIMIT/MAX_LIMIT are imported from src/app.js.
- Results are in catalogue (id) order, as the code returns them; paging assertions rely on that.
- Negative numbers and decimals count as 'not a whole number'; offset 0 and limit 1 are valid.
