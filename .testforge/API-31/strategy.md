# Test strategy: API-31 Search and page through products

Revision 1 · generated by TestForge

## Summary

GET /products filters the in-memory catalogue by case-insensitive name substring `q`, pages with `limit`/`offset` (default limit 20, capped at MAX_LIMIT), returns `{ total, items }`, and refuses non-whole-number limit/offset or limit < 1 with 400. Integration tests start the real http server on an OS-chosen port (as test/products.test.js does) and assert results against the exported PRODUCTS catalogue.

## Scope

**In scope**
- GET /products search by q (case-insensitive substring)
- listing without q
- limit/offset paging, total, default limit and MAX_LIMIT cap
- 400 for invalid limit/offset

**Out of scope**
- GET /products/:id and POST /orders (not part of this ticket)
- UI search box

## Acceptance criteria coverage

| AC | Criterion | Test cases |
|---|---|---|
| AC1 | `q` returns exactly the products whose name contains q, case-insensitively; without q every product matches. | TC1, TC2, TC3 |
| AC2 | Results are paged by limit and offset, the response's total is the number of all matches, and a limit above the maximum is capped to it. | TC3, TC4, TC5, TC6 |
| AC3 | A limit or offset that isn't a whole number, or a limit below 1, gets 400. | TC7, TC8, TC9 |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Case-insensitive matching breaks (e.g. only lowercasing one side) | high | TC1 searches with an upper-case query and checks the exact matching set. |
| Uncapped limit lets a client pull the whole catalogue | medium | TC5 asserts items length equals MAX_LIMIT for a larger limit. |
| Invalid paging params produce 500 or silent defaults | medium | TC6/TC7 table-driven 400 checks. |

## Test case detail

### TC1: matches names containing q in any case

*integration · vitest · positive · critical priority* — covers AC1

**Preconditions**
- server listening on port 0

**Steps**
1. GET /products?q=TEA&limit=50

**Expected:** 200; total equals the count of PRODUCTS whose lower-cased name includes 'tea' (Teapot, Tea strainer = 30), and items' ids equal the first page of those ids in order; every name contains 'tea' case-insensitively.

**Test data:** q=TEA

**Rationale:** Core search behaviour and case-insensitivity.

### TC2: returns no products when nothing matches q

*integration · vitest · negative · medium priority* — covers AC1

**Steps**
1. GET /products?q=zzz-no-such-product

**Expected:** 200 with { total: 0, items: [] }

**Rationale:** Filter really excludes non-matches.

### TC3: lists every product when q is absent

*integration · vitest · positive · high priority* — covers AC1, AC2

**Steps**
1. GET /products

**Expected:** 200; total equals PRODUCTS.length (120); items are the first DEFAULT_LIMIT products in id order.

**Rationale:** No-q listing and default page size.

### TC4: returns the page selected by limit and offset with the total of all matches

*integration · vitest · positive · critical priority* — covers AC2

**Steps**
1. GET /products?q=kettle&limit=5&offset=5

**Expected:** 200; total is 15 (all Kettle matches); items are matches 6-10 by id.

**Rationale:** Paging with a filter and total semantics.

### TC5: caps a limit above the maximum

*integration · vitest · edge · high priority* — covers AC2

**Steps**
1. GET /products?limit=MAX_LIMIT+1 and ?limit=1000

**Expected:** 200; items length equals MAX_LIMIT (50); total 120.

**Rationale:** Large limits are capped.

### TC6: returns an empty page when offset is past the last match

*integration · vitest · edge · medium priority* — covers AC2

**Steps**
1. GET /products?offset=120

**Expected:** 200; total 120, items [].

**Rationale:** Boundary of offset.

### TC7: refuses a limit that is not a whole number or below 1 with 400

*integration · vitest · negative · high priority* — covers AC3

**Steps**
1. GET /products?limit=<v> for v in 0, -1, 1.5, abc, empty

**Expected:** 400 with a JSON body having an error string, for each value.

**Test data:** 0, -1, 1.5, abc, ''

**Rationale:** Validation of limit.

### TC8: refuses an offset that is not a whole number with 400

*integration · vitest · negative · high priority* — covers AC3

**Steps**
1. GET /products?offset=<v> for v in -1, 2.5, abc

**Expected:** 400 for each value; offset=0 (TC3) is accepted.

**Test data:** -1, 2.5, abc

**Rationale:** Validation of offset.

### TC9: accepts a limit of 1

*integration · vitest · edge · medium priority* — covers AC3

**Steps**
1. GET /products?limit=1

**Expected:** 200 with exactly one item (id 1), total 120.

**Rationale:** Lower boundary of limit is accepted, not refused.

## Assumptions

- The cap is the code's MAX_LIMIT (50), not the README's 100 (asked as Q1); tests import MAX_LIMIT and DEFAULT_LIMIT from src/app.js.
- Expected results are derived from the exported PRODUCTS array (filtering by name, in catalogue/id order), not hard-coded copies of app logic beyond the plain filter definition in the AC.
- The real server runs in-process; nothing is faked. GET /products is read-only, so sharing one server per file is safe.
